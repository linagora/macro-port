# ADR-0007: Redaction of a report for sharing

Date: 2026-10-21 · Status: proposed (to validate) · Decided by: night agent for ticket #52, to be validated by Michel-Marie Maudet (LINAGORA)

## Context

SPEC section 8 gives the table of `--redact`: a keyed HMAC-SHA256, cut to 16 hexadecimal characters, replaces the paths, the roots and the name of the VBA project; the snippets are removed; the messages of the errors read `[redacted]`; the references stay; the names of the modules and procedures stay unless `--redact-identifiers` hashes them. ACCEPTANCE A6 checks the result: no snippet, no clear path or root, the same key gives the same output, no key gives other hashes in each run, and with `--redact-identifiers` no module or procedure name.

The SPEC leaves open:

- who draws the random key, since `macroport-core` is pure and may not draw random bytes;
- what "module and procedure names" covers: the report writes the names of the project in more places than the list of modules and procedures (the stream of a module, the procedures that a procedure calls, the module and the procedure of a signal, the first part of the name of an API);
- how "the original extension" survives when the text after the last dot can itself be a name that the redaction hides;
- whether the order of the files, which follows their paths, changes;
- how the JSON, the HTML and the CSV stay the same report;
- what `--no-snippets` does alone, and which options go with `--redact`.

## Decisions

**One rewrite of the model.** `macroport_core::redact::Redaction` rewrites the `Report` in place. The CLI applies it once, after the scan and before any report is rendered, so that the JSON, the HTML and the CSV carry the same values and no renderer knows about the key or the table. `redact::remove_snippets` is the part that needs no key, and what `--no-snippets` runs.

**Hash.** The first 8 bytes of the HMAC-SHA256 of the UTF-8 text under the key, written as 16 lowercase hexadecimal digits. The same text gives the same hash wherever it appears, which keeps the links of the report: the module that a signal names is the module of the list. With 64 bits, a collision takes billions of distinct names to be likely, and it would merge two names in a report, not reveal one.

**Key.** The core draws nothing: `Redaction::new(key, identifiers)` takes the bytes of the key, of any length (the `hmac` crate types a failure that no key raises, and the core hands it on as `KeyError` instead of panicking). In the CLI, `--redact-key KEY` gives the bytes of the argument. Without it, the CLI draws 32 random bytes with `getrandom` (ADR-0002; the only use of randomness in the program), once per run and before the scan, and neither prints nor writes them: two runs cannot be linked. A system that gives no random bytes is known before minutes of analysis: exit code 3 with `cli-error-key`. An empty `--redact-key` is a usage error (exit code 2): the HMAC under an empty key is a function that anyone can compute. The hashes are as strong as the key: with a short key, whoever holds a report can test guesses of paths and names. `--deterministic` does not fix the random key (it fixes the date and the duration, SPEC M4): a test that needs the same bytes passes `--redact-key`.

**Paths and roots.** The hash of the whole path as the report gives it, then a dot and the extension of the last name if, ignoring case, it is one of the twelve that a scan reads (SPEC M4), written as it was. Any other text after the last dot could be part of a name that the redaction hides (`invoice.acme-corp`, or a directory given as a root, `reports.2024`). This departs from the row of the table in SPEC section 8, `hmac(path)` + original extension, which keeps any extension: the two give the same result for every file that a walk collects, and differ for a root that is a directory with a dot in its name or a file that was asked for by name with another extension. The core holds its own copy of the twelve (`KEPT_EXTENSIONS`, since the walk belongs to the CLI), and a test of the CLI checks that the two lists are equal. The whole path is hashed in one piece, so the report does not show the depth of the tree or which files share a directory.

**Project name.** Hashed as written. Nothing else in the report names the project, so there is nothing for the hash to stay consistent with.

**Identifiers** (`--redact-identifiers`). Every name that the project defines and the report holds: `name` and `stream_name` of a module, `name` of a procedure, the entries of `calls`, and `module` and `procedure` of the signals of a file, a module and a procedure. VBA ignores case, so a name is lowercased before it is hashed: `Module1` in a definition and `MODULE1` in a call give one hash. Modules and procedures share one namespace. An entry of `calls` is cut at the dots and each part is hashed by itself, so that `Module1.Run` stays linked to the module and the procedure it names (the schema says that `calls` lists procedures of the same project, so every part is a name of the project).

The name of an API is hashed by its first part when the project defines that part, as a module, a stream or a procedure: `Sheet1.Range.Value` in a project with a module `Sheet1` becomes `<hash>.Range.Value`, and the hash is the one of `modules[].name`. The rest of the chain belongs to the object model and stays. A name whose first part is not defined by the project stays whole (`Range.Value`, `CreateObject:Scripting.Dictionary`), and so does a defined name further along the chain. Without this, `modules[].name` would be hashed and the same name would still be read in clear in the chains of every procedure that uses the module. The rule needs no list of the names of the object model: it asks only whether the project defines the root. The standard document modules (`ThisWorkbook`, `Sheet1`) are modules of the project, so they are hashed like the others.

**What stays.** The references, `apis[].name` (object model members, functions and ProgIDs, normalised, but for the first part when the project defines it), the metrics, the families, the signals (ids, severities, line numbers), the traits, the statuses, the ids of rules, the codes of errors, the `summary`, and the hashes of contents `files[].sha256` and `modules[].source_sha256`. The report holds no name of a declaration of the project: `declarations` counts them.

**Text modules.** A `.bas`, `.cls` or `.frm` file is one module, named after the file without its extension (`module_name` in `crates/macroport-core/src/analyze/modules/text_file.rs`, PR #133). The module is a module like any other for the redaction, so the table of the SPEC applies: with `--redact` alone, the path of `Q3 budget.bas` is hashed and the module `Q3 budget` stays in `modules[].name`, in the module column of the CSV and in the `module` of the signals; `--redact-identifiers` hashes it. The help of `--redact-identifiers` says so.

**Order of the files.** The files are sorted again by hashed path, then by hash of content, as a report always is. Keeping the order of the clear paths would show it.

**The `redacted` flag.** `true` only with `--redact`, which hashes the paths. `--no-snippets` alone removes the snippets and leaves `redacted` false: its report still carries paths and names, and must not be taken for one that can be shared.

**Options.** `--redact-key` and `--redact-identifiers` require `--redact` (usage error, exit code 2): taken silently, `--redact-identifiers` alone would give a report with every name in it to someone who asked for them to be hidden. `--redact` includes `--no-snippets`. `file` has no privacy option: the SPEC gives them to `scan`, and `file` prints one report on the console of the person who runs it.

**Console.** Not redacted, since it shows nothing to hide: the progress and the summary give counts and the output directory typed by the user.

**A guard.** A test of the core walks `schema/report.schema.json` for every property that holds free text and compares them with a list that says what the redaction does with each (`FREE_TEXT` in `tests/redact.rs`). A field that the schema gains fails the test until someone decides it.

## Alternatives rejected

- **Redaction in each renderer.** Three implementations of one table, and a renderer that misses a field leaks in one format only.
- **Hashing the components of a path one by one.** It shows the depth of the tree and which files are siblings, and gives the same hash to the same directory name everywhere.
- **Keeping any extension.** The text after the last dot can be a name.
- **A namespace of hashes for each kind of name.** The entries of `calls` do not say whether a part is a module or a procedure. With one namespace, a module and a procedure that share a name get one hash, which links nothing that was not linked.
- **Folding the case of the project name.** It is not an identifier of the code, and nothing refers to it.
- **Hashing the module of a text file without `--redact-identifiers`.** It keeps the name of the file out of a report made with `--redact` alone, which is what a reader expects of a path that is hashed. It would make a name read differently according to where the module came from (`Module1` of a workbook stays, `Module1` of `Module1.bas` would not), and it needs the redaction to read `container` (`text_module`) and to hash the qualifiers of the calls that name the module. That is about twenty lines. Not done: the SPEC table says that the names of modules stay, and which reading is right is for the owner.
- **Printing the random key at the end of the run**, to let the person reproduce the hashes. It writes the means of linking the reports in a log. Whoever wants to link runs passes a key.
- **Setting `redacted` for `--no-snippets`.** A reader would take the paths for hashed.
- **A key from a file or an environment variable.** The SPEC fixes `--redact-key KEY`. A file or a variable would keep the key out of the list of processes; it can be added without changing the report. This is a scope choice, not a judgement on merit.

## Consequences

Points for the owner:

- **The hashes of contents stay**, `files[].sha256` (required by the schema) and `modules[].source_sha256`. Whoever holds a candidate file can check that a redacted report is about it, and two reports on the same file can be linked although each was made under a random key. SPEC section 8 says that a random key makes runs "unlinkable": this is not true of the content hashes. Keying them breaks their use as the identity of a file (looking up a sample in a database, for instance); dropping `sha256` changes the schema. The choice is yours.
- **`apis[].name` stays**, except for a first part that the project defines, and the SPEC's table does not list it. It holds ProgIDs (`CreateObject:Vendor.Component`), so a component of the organisation, or a library it references, can name the organisation. ACCEPTANCE A6 also says that "none of the string literals of the corpus" appears in a redacted output, which a ProgID kept in `apis[].name` contradicts to the letter. The check at the level of literals is written (`a_redacted_scan_of_the_corpus_shows_none_of_its_string_literals`) and takes A6 as "except the vocabulary of the report": it looks for the literals of the corpus that have six characters or more, except those that the tool also writes itself (in its schema, its rules, its messages, the codes of its errors) and the names that the report keeps (the references and `apis[].name`). It scans the corpus three times: without any option, to check that the search can find the literals at all (a report that the analysis has not filled would otherwise pass for one that hides everything); with `--redact`; and with `--redact-identifiers`. Since #156 and #157 the analysis fills `apis` and `calls` (14,932 and 2,239 entries over the corpus), and the sweep runs on them. A kept name next to the text of the report can spell a literal that neither holds (`Err.LastDllError ×6` in the HTML spells `Error `), so the search skips an occurrence that a kept name crosses; a kept name inside the literal excuses nothing. Since the security stage of M3 (#46) the analysis fills the signals too (32 of files, 56 of modules and 394 of procedures over the corpus), and the sweep runs on them. Options: keep ProgIDs as the vocabulary of the report, as now; hash those that no rule knows; or read A6 to the letter and hash every `apis[].name`, which takes away what the report is read for.
- **A6 and the table disagree for `--redact` alone.** The table keeps the names of modules and procedures, and a literal of the code can be one (`Application.OnTime Now, "Refresh"` with a procedure `Refresh`). The sweep of `--redact` therefore allows the names of the project as well, and only the sweep of `--redact-identifiers` reads A6 without that exception. The table wins; the alternative is to hash the names by default, which makes `--redact-identifiers` redundant.
- **A variable can root a chain.** The rule for `apis[].name` hashes a first part that the project defines as a module, a stream or a procedure. The report holds no list of the variables of a procedure. ADR-0011 (#156, M2) answers whether `apis[].name` can start with the name of a variable: every chain is an API, its first name included when that name is a variable (`ws.Cells.Clear`; the samples give `targetWorksheet.Columns.Cells.End.Offset.Row`). The name of a variable thus stays in clear under `--redact-identifiers`, and no test of this PR shows it, since the sweep allows what `apis[].name` keeps. Hashing it needs a rule for the variables, which the report does not list: yours to decide.
- **The references stay**, as the SPEC says. A reference to an internal library can identify the organisation (a hypothesis: I have not seen the display names of the references of a real project).
- **A text module keeps the name of its file** under `--redact` alone, since the module takes that name and the SPEC keeps the names of modules. The path is hashed, the file name is not, and a reader who sees `modules[].name` has the file name of a `.bas` file. If the names of the files are as sensitive as the paths, the module of a text file should be hashed by default (see the alternatives rejected for what that takes).

What follows from the decisions:

- A key on the command line shows in the list of processes and in the history of the shell.
- The redaction is tested on hand-written reports (`crates/macroport-core/tests/redact.rs`, `crates/macroport-cli/tests/scan_redact.rs`), with hashes computed apart, and the guard of the schema makes a new free-text field a decision. Three tests of `scan_redact.rs` need the modules that the analysis finds in the files of the corpus (the literals of the corpus are not shown; the names of the project are hashed; a text module is named after its file). They run on the corpus since PR #133 gave `analyze` the text modules, and one of them fails if the corpus has no call to hash.
- The core stays free of randomness for M5 too: `macroport-wasm` is to draw the key (ADR-0002 gives it `getrandom` with `wasm_js`) and hand it to `Redaction::new`. Its `analyze` redacts one file at a time, so a web app that aggregates the files of a fleet has to pass one `redactKey` for all of them, or the same name gets another hash in each file.
